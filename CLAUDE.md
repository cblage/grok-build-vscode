# CLAUDE.md — grok-build-vscode

VS Code sidebar extension for **SpaceXAI's Grok Build CLI**, driven by `grok agent stdio` over the [Agent Client Protocol (ACP)](https://agentclientprotocol.com). Thin client — all session state, MCP servers, subagents, memory, and plan-mode bookkeeping live in the CLI.

## Status

See [CHANGELOG.md](CHANGELOG.md) for the current version and full release history (the Marketplace/GitHub-published build can lag the local working tree). The whole test suite is **grok-free** — CI never spawns the binary; grok-dependent probes live separately in `research/*.cjs`. Plan mode is **enabled** and enforced client-side (see `research/plan-mode.md` § Resolution). Smoke-tested end-to-end on Linux, Windows-via-WSL, and the **native Windows build** (`irm https://x.ai/cli/install.ps1 | iex`) — `cli-locator` resolves `grok.cmd`/`grok.exe` and `terminal-manager` runs the agent's commands under PowerShell on Windows (`pwsh`→`powershell`, mirroring the standalone CLI; #46), `/bin/sh` elsewhere.

This file is the project map: it describes the **current** architecture, not a per-version log.

**Editing discipline — keep this file lean.** When behavior changes, *rewrite* the affected lines to the new current state; do **not** append a note about what changed or why the old way was wrong. Concretely, none of these belong here:
- version-by-version history or "fixed in 0.2.x / removed in 1.4.x" → [CHANGELOG.md](CHANGELOG.md);
- bug post-mortems / "used to… / this broke because…" narrative → a code comment or `research/*.md`;
- evidence dumps ("one capture: 17.7s", "a real case: 74 messages") → `research/*`.

State the rule, name the function / constant / config-key an agent would grep for, and link the deep-dive — **one fact, one home**. Every feature already has a `research/*.md`; `docs/architecture.md` holds the event-flow detail; [docs/ACP-feedback.md](docs/ACP-feedback.md) is the upstream-facing summary of grok-CLI/ACP friction, agent-family wire differences, and our workarounds (update it when a new workaround lands or an old one becomes obsolete). If a paragraph explains *how we found* a bug rather than *how the code behaves now*, it's in the wrong file.

**Grok CLI compatibility.** `maybeUpdateCliOnUpgrade` runs from session start and updates once after an extension-version change; a fresh install only records `CLI_UPDATE_VERSION_KEY`. Each start then reads `grok --version` via `probeVersionOutput` (one short retry on empty/unparseable — a slow first spawn must not cost Plan). On Windows, `isStdioBrokenGrokVersion` identifies only the known-broken **0.2.61–0.2.70** startup range and `maybePinBrokenCli` proactively pins it to `GROK_STDIO_DOWNGRADE_TARGET`; `shouldReactivelyDowngrade` → `downgradeBrokenCli` remains the observed-failure backstop above that target. `GROK_REQUIRED_VERSION` and the recovery target share the current supported version (**0.2.117**). `decidePlanModeAvailability` is fail-closed: a parseable CLI below the floor latches Plan off for that session (`planModeVersionVerified:true`); an unreadable probe also disables Plan but stays **re-checkable** (`planModeVersionVerified:false`, `planModeAvailability.recheckable`) so picking Plan runs `recheckPlanModeAvailability` without restarting — only a verified-old answer hard-disables the picker row. Agent/Auto accept still run either way. Agent-initiated/restored Plan raises the client safety gate and returns to Agent. A live untrusted planning turn is cancelled, and the gate drops only after both its `session/prompt` settles and `session/set_mode` confirms Agent; a bounded warning leaves the gate visibly raised if recovery stalls. A stray `exit_plan_mode` receives an error rather than an unsafe native verdict. A later session whose version meets the floor starts with Plan enabled again; existing old processes remain restricted. Exact regression history and probes: `research/stdio-eof-regression.md`; timeline: [CHANGELOG.md](CHANGELOG.md).

## Session pool (Agent Dashboard)

The sidebar runs a **pool of live sessions** (one `grok agent stdio` process each) with one `focused` (the one rendered). Each session's state is a `Session` (`src/session.ts`); the sidebar holds `focused` + a `Set<Session>` `pool`. **Re-focus is lossless**: every session buffers the webview posts that built its chat (`Session.buffer`), so `focusSession` is `clearMessages` + replay of that buffer — no grok reload, no kill, even mid-turn/mid-approval. Clicking a *cold* session (no live process — reaped or pre-window) loads it from disk into a fresh member (`openSession`); a live one re-focuses instantly. Two guards keep it safe: a **per-session `gen`** (bumped only when *that* session's client is torn down, captured by handlers when wired) so a backgrounded session's in-flight events aren't judged stale when focus moves; and **session-scoped `emit(session,…)`** (buffers + forwards only when focused) vs UI-wide `post(…)` (status dots, sessions list). **Status dots.** Every history row shows a dot whose color is a *derived* value (the pure `computeDot` in `src/session-pool.ts`), not the raw `status`: **gray** at rest (idle / read / cold / loaded-from-disk all collapse to one gray — the user never learns warm-vs-cold), **blue** working, **yellow** needs-you, **green** finished-and-unread, **red** errored-and-unread. The green/red is an **unread badge**, not a live state: a turn that ends while the session is *not* focused sets a persisted `unread`/`unreadError` flag in `SessionMetaOverride` (globalState); focusing/opening the session clears it (`markRead`). So the badge **survives reaping AND reload** (it's meta-backed, decoupled from the live process) — that's the payoff: come back and the green dots are exactly the sessions with results you haven't seen. No timer/decay — a never-opened session stays green (it *is* still unread). `computeDot({liveStatus, unread, unreadError})` precedence: working → needs-you → unread(error?) → none. Dots are pushed one-at-a-time via `pushDot`→`sessionDot` (cheap, no disk read) plus a full `dots` map (`dotForId` over disk entries + pool) on each list refresh; palette in CSS — Working=`--vscode-charts-blue`, Needs-you=`--vscode-charts-yellow`, unread=`--vscode-charts-green`, error=`--vscode-errorForeground`, none/default=`--vscode-descriptionForeground`. **Reaping** is the pure `selectReapable` (`src/session-pool.ts`): an **idle TTL** (untouched ≥1h, swept every 5 min) + an **LRU cap** (~8 live; least-recently-used eligible evicted past it), but it **never** reaps the focused or a `working`/`needs-you` session (so the cap can be exceeded when everything spare is busy, by design). Reaping is silent — kill the process, recompute the dot (an unread reaped session **stays green**; a read one goes gray); re-click reloads from disk. Recency (`Session.lastActiveAt`) is stamped on create/focus/made-busy via `touch`. **CLI-update guard:** the explicit *Update Grok Build CLI* action (`updateGrokCliOnDemand`) confirms before tearing the pool down if any session is `working`/`needs-you`; the silent startup auto-update has nothing in flight by construction, so it doesn't ask. Per-workspace scope. The impure `voice-recorder`/`voice-streamer` (ffmpeg spawn + STT fetch/WebSocket) are smoke-tested manually via the `research/voice-*.cjs` probes (`voice-stt-probe`, `voice-e2e-verify`, `voice-stream-probe`, `voice-stream-verify`, `voice-cost-probe`).

**Empty-session cleanup (#24, #97).** Two mechanisms, and the split matters. `parkFocused` / `parkRemoteSession` use `hasHistory === false` to delete an untouched session's on-disk dir the moment the user leaves it, so at most one untitled **New session** exists per view. `sweepEmptySessions` covers what parking cannot reach — a window closed without a prompt, a crashed host, a remote tab that vanished — and runs on activation and after every new/opened session, scoped to that session's repo. It deletes only when `isEmptySession` confirms **zero real user queries** in `chat_history.jsonl`; that content check is authoritative regardless of `num_messages` (an agentic legacy primer turn could balloon past any gate), and `EMPTY_PRIMER_MAX_MESSAGES` now gates only the no-content title fallback. **The predicate used to require our hidden primer, which made it a silent no-op for every session created after v2.2.0 retired it** — that is #97, and the lesson is that a compatibility check keyed on a thing we stopped emitting stops being a check at all. Guards, each load-bearing: live sessions, sessions with a load reservation in flight, renamed, pinned, worktree-bound, `session_kind: "subagent"`, an unreadable (as opposed to absent) history file, and anything newer than `SWEEP_MIN_AGE_MS` (30 min). That last one is sized for the case this process cannot see: **another VS Code window's live sessions are invisible here**, so the delay — plus the fact that only a zero-user-message session is ever swept, and grok re-persists it on its next turn — is what bounds a cross-window delete. It costs nothing, because an orphan is stamped when its window opened and is already old by the next activation. `historyIsIntelligible` is the other interlock and the more important one: "no real user queries" is evidence of emptiness **only if the file could be parsed at all**, because a reader that skips what it doesn't recognize cannot tell "nothing was said" from "grok changed the format" — without it a single CLI schema change turns the sweep into a shredder that finds every session empty. `provenNonEmpty` caches the ids a repo has already cleared so repeat sweeps cost a readdir plus stats, not a re-read of every summary. **Verify a predicate change against a real store before shipping it** (`isEmptySession` over `~/.grok`, reporting rather than deleting): the pre-ship dry run covered 1435 sessions and had to show zero candidates carrying a real title or any user query.

**History row names (#96).** Precedence is `customName` → grok's own title (`cliSessionTitle`: `session_summary`, else `generated_title`, both rejected when primer-derived) → `autoName` → `Untitled (<date>)`. `maybeGenerateTitle` writes the truncated first user message to **`autoName`, never `customName`** — a name the user typed and a name we guessed are different claims, and writing the guess into the rename field made it permanent, so the CLI's own title for the same session could never surface. Sessions named before this keep what they have: an auto title already sitting in `customName` is indistinguishable from a rename, and guessing wrong there would discard names people typed.

## History pagination

The history popover loads sessions **one page at a time** (`SESSION_PAGE_SIZE = 100`, newest-first) so it stays responsive with thousands of sessions on disk. The cost of the old behavior (read + `JSON.parse` *every* `summary.json` on every open, then render every row) grew linearly and stalled the popover at scale.

**Scope — the selected repo.** `discoverRepos` (`sessions.ts`, pure) enumerates cwd catalogs under `<grokHome>/sessions`, rejecting temp roots and `<grokHome>/worktrees` (a worktree isn't a checkout you choose between). `postSessionsList` indexes the selected repo **plus the worktrees belonging to the same checkout** (`sessionCwdsForRepo` uses the selection's nearest git root when available, otherwise its exact catalog cwd, then `worktreeCwdsForRepo` requires equality with recorded `sourceGitRoot`; `mergeSessionIndexes` combines their catalogs) — this keeps a selected subdirectory and its repository's registered worktrees together without letting an independent nested checkout inherit its parent's sessions. A worktree whose parent identity cannot be established is excluded. `trustedCwds` (the workspace root) bypasses the managed-worktree exclusion so the selection always names a catalog row, or `clearAllSessions`/`selectRepo` would silently no-op. The picker is **remote-only** (`#repo-btn`; in VS Code the window already *is* the repo) and, because the relay serves a client that can outrun the installed extension, the chip appears only once a `repos` frame has arrived — an older host that never sends one shows no chip rather than a dead control. Selection and active conversation are **per browser tab**: `RemoteClientState` maps the current opaque relay client id to its cwd and `Session`; live chat/session UI/voice messages target only that id. `media/chat.js` stores `{repoCwd,id,cwd}` in device-scoped `sessionStorage`, clears it only for an explicit repo/New choice, and posts `selectRepo` + the existing `resumeSession` after each reconnect snapshot. The host attaches that request to an ownerless live pool member (no duplicate process), cold-loads it only when absent, and visibly refuses a missing/deleted session or a session already owned by another tab/VS Code. **Ownership follows the live composer, not focus:** every live session created or adopted by the VS Code dashboard remains locally owned while backgrounded; a departed remote client's member becomes ownerless and reclaimable. Resume transitions serialize by Grok session id; New serializes by client id, while turn/control traffic remains unlocked. The local VS Code webview keeps its independent workspace-root `focused` session. Remote cwd-bearing actions remain gated by `allowRemoteRepoTarget`; roster reconciliation deletes departed client ownership without disposing the pooled session so a new relay id can reclaim it. Pins remain global metadata, while the selected row is per tab.

**Two pure primitives** replace the monolithic full-scan `listSessions` (which is kept only for callers that genuinely need the whole list):

- `indexSessions({fs, grokHome, cwd})` — one `stat` per session dir, **no reads/parses**, returning every id ordered newest-first by `summary.json` **mtime**. mtime is the cheap last-activity proxy: grok rewrites that file (it holds `updated_at`) on every turn. We sort by mtime here *because the id is a UUIDv7 whose timestamp is creation, not last activity* — id-sort would be wrong.
- `readSessionEntries({fs, grokHome, cwd, ids, overrides})` — reads + parses `summary.json` for **exactly the given ids** (the visible page) and applies `customName` overrides. The exact `updated_at` order is re-applied within the loaded page (mtime is only an approximate sort key).

**Host orchestration** (`postSessionsList` in `sidebar.ts`): `indexSessions` orders everything cheaply; a `mtimeById` map drives an **mtime-keyed read cache** (`sessionCache`, `readEntriesCached`) so a re-open / load-more / search reads only entries whose `summary.json` actually changed — steady-state opens cost ~zero reads. It posts `{type:"sessions", entries, activeId, dots, offset, total, hasMore, query}`. **Search** is server-side and complete: a non-empty `query` warms the whole catalog once (cache-backed) and filters by display name across **all** sessions, not just the loaded page. The cache is invalidated on `rename` (changes displayName without touching mtime), `delete`, and `clearAll`. **Live-session synthesis:** a brand-new session has no `summary.json` yet, so on the **first, unfiltered page** `postSessionsList` injects a synthesized `liveSessionEntry` (pinned newest-first) for any live `pool` member whose `activeSessionId` isn't on disk, named from the best in-memory source (generated/renamed `customName` → first user message → `"New session"`); the next refresh replaces it once grok flushes the file. `hasMore` is computed from the on-disk page *before* injection (load-more pages are disk-only), and these ids are never on disk so they can't duplicate onto a later page.

**Webview** (`media/chat.js`): `offset === 0` replaces the list, `offset > 0` appends (de-duped by id); a scroll-near-bottom listener requests the next page (`hasMore`/`sessionLoading` guards keep it to one request per boundary); the search box posts a **debounced** (180ms) `listSessions` with the query; a host-driven refresh that arrives unfiltered while a search is active triggers a **sticky-search** re-request so the filtered view isn't clobbered. The "Clear all" footer shows when any non-active session exists (loaded *or* on a later page, via `total`). **Popover positioning:** `positionDropdownPopover` **right-aligns** the popover to the panel edge (`right: 6px`/`left: auto`) and grows it leftward — width-independent, no measurement. It **caps min/max width to the panel** (`min(360|280, parentWidth − 2·EDGE)`, overriding the CSS `min-width: 280px`/`max-width: 360px`) so a long session name **ellipsizes** in a narrow panel instead of overflowing. **Resize/hide:** a `window` `resize` listener re-fits it live while open; a `document` `visibilitychange` listener `closePopovers()` when the view is hidden (a resize while hidden fires no event, so close rather than reappear stale).

**Perf simulation** (`npm run test:perf`, `test/sessions.perf.ts` via `vitest.perf.config.ts`) — opt-in, out of `npm test`/CI. At N=5000 it asserts the op counts: first open drops file reads from **5000 → 100** (~98%), steady-state re-open is **0 reads** (mtime cache), search warms once then **0 reads**, with a modeled-latency projection (~3250ms → ~310ms) and a real in-memory parse-cost wall-clock (~2.7x, disk-latency-free lower bound).

### Test taxonomy — three layers

There are **three** kinds of tests, and it matters which is which:

1. **`npm test` — grok-free unit/DOM/integration suite (2659 tests).** Pure logic, happy-dom tests that drive the real `media/chat.js`, a real-`/bin/sh` TerminalManager smoke, and a fake-CLI ACP integration suite (`test/fixtures/fake-grok-acp.cjs`). **Never spawns the real `grok` binary.** Runs in a few seconds with no network, no login, no subscription. This is the floor — every change keeps it green. (Two separate opt-in suites live outside `npm test`: `npm run test:perf` runs the session-history perf simulation — `test/*.perf.ts` via `vitest.perf.config.ts` — and `npm run test:integration` runs the `@vscode/test-electron` smoke below; both are matched only by their own config so they stay out of `npm test`.)
2. **CI — the *same* suite, plus a REQUIRED Electron smoke.** `.github/workflows/ci.yml`'s `test` job runs `npm ci && npm run compile && npm test && npm run package` on a clean Ubuntu box — **CI's `test` job ≡ layer 1, verbatim** (no `grok` binary, no auth, no subscription, so it *cannot* touch the real CLI — the whole reason layer 1 is grok-free). A second job, `integration`, runs the `@vscode/test-electron` smoke under `xvfb` (`npm run test:integration` — activate the extension, assert commands registered, resolve the webview via the *missing-CLI* onboarding path so it needs no grok). It's a **required gate** (validated passing against a real VS Code Extension Host before landing; if a Linux/xvfb quirk ever surfaces, fix it rather than demoting the gate). The smoke is still grok-free — it exercises host glue (activation, `getHtml`/CSP, `localResourceRoots`, command registration) the unit suite structurally can't reach. Compiles in isolation (`integration/tsconfig.json` → `out-integration/`), so it's out of `npm test` and the extension build.
3. **`npm run test:live` — on-demand pre-release suite against REAL grok (`scripts/live-tests.cjs`).** It covers the real handshake, capability drift, prompt/cancel/interject, fork/parallel/restore, plan enforcement, rewind, usage, and generative surfaces. The plan lane now uses native verdicts: its first same-turn `exit_plan_mode` response is `cancelled`, the second is `approved`, and the gate is lowered inside that response callback before implementation continues; `plan-cancel-rewind` uses native `abandoned` with no primer or marker turns. It reuses the compiled dispatch/gate/rewind modules and shipped webview helpers. The release scripts run it by default, but it needs a logged-in grok, burns credits, and never belongs in `npm test` or CI. A SKIP does not fail the gate; research probes remain manual one-offs.

**So:** local `npm test` == CI's `test` job (both grok-free) — but that is NOT all of CI: a second required job runs the grok-free Electron smoke, so `npm test` alone is a subset of what must pass. Mirror it with `npm run test:integration`, which `release.*` now gates on too. The real-grok tests are a separate, mandatory pre-release gate — always run before a tag/release (no need to ask), never on every commit.

### grok CLI version + updating

The native-Windows build (`irm https://x.ai/cli/install.ps1 | iex`) installs from the **stable** channel. The extension pins Windows to the supported build (`GROK_STDIO_DOWNGRADE_TARGET` in [src/cli-locator.ts](src/cli-locator.ts); see § Status → Grok CLI compatibility). **grok does not auto-update.** Updating is the explicit `grok update` command: `--check [--json]` checks without installing, bare `grok update` installs the latest on the current channel, `--stable` (default, weekly) / `--alpha` switch channels, `--version <X.Y.Z>` pins a build. `grok update` can only rename the binary when no grok process holds it open (else *"cannot rename locked executable"*), so the extension's update path tears the whole pool down and **awaits each process's actual exit** before updating; on Windows it `taskkill /T /F`-kills the process **tree** (grok backgrounds children that keep the binary locked) and retries once on a lingering lock (`isLockedBinaryError`). Re-run `npm run test:live` after any CLI update — the wire format is the thing that drifts.

## ACP surfaces implemented

- `initialize` → `session/new` / `session/load` → `session/set_model` → `session/prompt` lifecycle
- **Model switching is agent-aware.** Models belong to agent types (`grok-build`/`grok-build-plan` vs. Composer's `cursor`). The CLI locks that binding after the first turn, so a cross-agent live switch raises `MODEL_SWITCH_INCOMPATIBLE_AGENT`; `switchModel` persists the pick and restarts, with `newSession` applying the model before the first turn. Versioned IDs resolve through `resolveModelId`, and the webview recomputes the per-model context window on `modelChanged`.
- Streaming `agent_message_chunk` + `agent_thought_chunk`
- Sessions: list/resume via `session/load` (grok stores them at `~/.grok/sessions/<urlencoded-cwd>/<id>/`); rename/delete metadata in `context.globalState["grok.sessionMeta"]`. We never edit grok's own session files. **Per-session delete** is the trash button on each history row (`deleteSession` → `deleteSessionDir`), **including the active one**: the host disposes the live `Session` *before* touching the disk — the live CLI owns the conversation and re-persists it, which is why deleting it first simply did not stick — then re-homes every watcher (`newLocalSession`/`startSession` for the desk, `newRemoteSession` per remote tab) onto a fresh conversation in the same repo. Still refused: a live conversation the requester is *not* the one watching. Gated on the `deleteActiveSession` host capability so an older host is never offered a control it answers with a refusal. **Clear all** (#19) is a footer button in the history popover (shown only when ≥1 non-active session exists) → `clearAllSessions` in `sidebar.ts`: a confirmed sweep of every session dir for the *selected repo* *except* the focused one, via the pure `clearSessions({fs, grokHome, cwd, exceptId})` in `sessions.ts` (best-effort — a locked dir is skipped, not thrown), then purges the removed ids' `grok.sessionMeta` overrides and tears down any backgrounded live pool members it deleted. **Scale (history pagination):** the popover loads **one page at a time** (newest-first by last activity) so it stays fast with thousands of sessions — see § History pagination. Clear-all is the relief valve for an overgrown store; the pagination is the steady-state fix. **The name is also chrome, not just a history row (3.1.0):** the focused conversation's title sits in `.top-bar` (`#session-name-chip`) in VS Code and in `#session-head-title` remotely, ellipsised with the full text as its `title`, and renames in place — pencil on hover, tap on touch (`@media (hover: none)` unhides the pencil), Enter/blur commits, Escape or an unchanged/empty value cancels. It reuses the existing `renameSession` message; only the *display* needed a new one. That new `sessionName` HostMsg exists because the webview's `state.sessions` is populated by the history popover and follows its search box — VS Code cannot read a name out of a list it has never opened. It carries the same string `sessionDisplayName` gives a history row (so the two can't disagree) and is re-sent wherever the view's conversation changes: `startSession`, `postSessionsList`, the remote snapshot, and `focusRemoteSession` — that last one because it clears the client and then builds its own targeted list instead of going through `postSessionsList`, which is a real regression an integration test now pins. The client gates the rename affordance on having *received* the message, never on a version, so an older host simply shows no pencil.
- Handlers (mandatory or the agent crashes): `fs/read_text_file`, `fs/write_text_file`, `terminal/{create,output,wait_for_exit,kill,release}`
- `session/request_permission` → chat card with `allow-always` / `allow-once` / `reject-once`, diff editor preview for `kind:"edit"`. **Keyboard (#68):** the CLI's option order isn't guaranteed, so `orderPermissionOptions` (webview-helpers.js) sorts approve-first/reject-last (unknown kinds rank between — never the default, never below reject) and `defaultPermissionIndex` picks the tab stop: `allow_once` only, **never `allow_always`** (a keystroke must not widen scope for the session). The card takes focus only when `shouldFocusPermissionCard` says the composer is genuinely idle — empty, not replaying, no IME composition in flight (`state.composingIME`, since a preedit buffer isn't in `input.value`). Roving tabindex + arrows move within the group; Escape returns to the composer **without answering** (never an implicit reject); and `isTypeThroughKey` redirects a printable keystroke to the composer instead of activating a button, which is what makes taking focus free. The reporter's "wait 1s after typing" timer is deliberately **not** implemented — the action a key takes must follow visible focus, never invisible timing, least of all when that action approves a command.
- `x.ai/ask_user_question` (#12) → inline question card. Renders each question's options (single question + single-select resolves on one click; otherwise pick-then-Submit; Skip → cancel) and replies `{ outcome: "accepted", answers, annotations }` (or `cancelled`) — `answers` keyed by question text → chosen label; the reply **must** carry `outcome` (an empty ACK is rejected). On answer the card collapses to the question + a green `✓ <choice>`. On resume the question replays as a `tool_call` (questions in `rawInput`) + completed `tool_call_update` (answer text); chat.js suppresses the generic tool chip and rebuilds a read-only "You answered" card from that replay. Pure builders: `makeQuestionResponse` (`acp-dispatch.ts`), `buildQuestionAnswers` (`webview-helpers.js`). Wire format: `research/ask-user-question.md`. **The free-text "Other" is ours, not the CLI's (#85):** the tool contract promises every question carries one, the CLI usually does not send it, and the first fix keyed the input on a supplied option labelled `other` — so in practice most cards had no free-text path at all. `addQuestionCard` appends the option itself when absent (case-insensitive dedupe, so a CLI that does send one never gets two) and the typed value replaces the synthetic label inside the existing `answers` map — no ACP change, so it works against whatever grok is installed. Consequence worth knowing: `hasOther` is now always true, so the Submit/Skip footer renders on single-question cards that used to resolve on one click. This is decoupled from the permission flow on purpose: the diff `content` block (`type:"diff"`, with `oldText`/`newText` = the replaced region) rides the `tool_call_update` regardless of permission mode, and whether a permission card even appears is grok-build/platform-dependent, not a config toggle (verified 0.2.99: default config sends 0 permission requests for in-workspace edits; `research/edit-diff.md`). The pure `computeLineDiff(oldText,newText)` (`webview-helpers.js` — LCS backtrack, CRLF-normalized for compare+display, empty region = 0 lines so a new file reads as pure adds) yields the `+/−` counts and the diff rows. **A block is expanded into one hunk per replaced SITE** (`extractDiffSites` in chat.js): the block's `oldText`/`newText` is the search *pattern*, so a `replace_all` block describes only the token and alone renders 148 occurrences as one meaningless `+1 −1` — `_meta.details[]` is the complete account (one entry per site, `{old_string, old_line, new_string, new_line, context_before, context_after, line_prefix}`, real 1-based **post-edit** file lines; verified 12/12 against ground truth, `research/edit-diff-lines.log`). Per delivery shape: **completed + session/load** carry `details[]` → a site each, rendered `line_prefix + old_string` → `line_prefix + new_string` (there is **no `line_suffix`** on the wire, so the line's tail is genuinely unavailable and is not reconstructed); the **echo** carries no `details[]`, only a first-site-only block `_meta.{old_line,new_line}` → one approximate hunk the completed update then upgrades; neither (a whole-file Write's `_meta:{}`) → one hunk seeded 1 via `fileLineOr1` (also the guard for absent/bogus — 0/negative/non-number). A creation (`old_string:""`) takes no prefix, so a new file stays pure adds instead of the prefix becoming a phantom del. `buildInlineDiffRegion(hunks)` renders them **Codex-style**: **ONE `.tool-diff-region` per BLOCK holding N hunks** (never one region per site — 148 sites would otherwise stack 148 boxes) of `.tdl` rows, each a `[+/− sign][line-number gutter][code]` grid with a colored left-border stripe + subtle per-line tint; each hunk seeds its own gutter, and a quiet `.tdl-sep` hairline parts **non-contiguous** hunks (never before the first, never between contiguous ones). the region shows the first `DIFF_PREVIEW_LINES` (12) rows with a **"Show more"/"Show less"** toggle that grows it **inline, no inner scroll** (#71; remote-safe, unlike the host-local `open diff →`); `MAX_INLINE_DIFF_LINES`=400 is the hard budget **across** a block's hunks (1000 sites must not paint 2000 rows), the `open diff →` remainder note hidden until expanded — but the `+N −M` is summed over **every** site *before* the cap, so a capped render still reports the true magnitude. Del shows the old-side number, add/context the new-side. The gutter track sizes per region to the widest number rendered (`--tdl-num-w` = `max(4ch, digits+1)`) — 4ch through 999, wider only for a 1000+ line file. The `+/−` glyph is a color-blind affordance beside the border. Colors are **Codex's exact palette** (`--tdiff-*` CSS vars, dark default + `body.vscode-light` override): add `#40c977`/`#00a240`, del `#fa423e`/`#ba2623`, backgrounds the same at 23%/15% alpha — reused for the `+N −M` stat too. `applyToolDiffs`/`attachDiffPreviewToToolItem` handle BOTH the live `tool_call_update` and the session-load completed `tool_call` replay shapes (#30); a single call can carry multiple `diff` blocks (rendered as an array), each getting exactly **one** `open diff →` (per-site would emit 148 buttons; its payload stays the block's own `oldText`/`newText`). **grok reports each edit's diff twice** — an optimistic pre-write echo, then the authoritative completed update — and for a whole-file Write that OVERWRITES a file the echo carries `oldText:""` while the completed one carries the real prior content, so the echo must not win: idempotency is keyed on `item._diffSig` (the serialized diffs, **sites included**, so the `details[]`-seeded render outranks the echo's approximate one), making an identical replay a no-op while a *different* later diff repaints the row (reusing the detail node, or `wireCommandToggle`'s listener would strand + double-bind). **Totals paint as each edit lands**, not at batch close — the data is on the wire ~2.2–3.3s before the turn ends (`research/edit-diff-timing-probe.cjs`). `recomputeGroupDiffTotals` *recomputes* from the rows' `_diffStat` (so a corrected row replaces rather than double-counts) and `paintGroupDiffTotals` owns a `.tool-group-diff-totals` span, re-painted after each of the two things that wipe the header: `addToToolGroup`'s per-call `hdr.innerHTML` rebuild and `closeToolGroup`'s label reset. Painting earlier still, from the initial `tool_call`'s `rawInput`, is deliberately NOT done: it buys ~30ms and reconstructs the same wrong `oldText:""` for a Write. None of this expands anything — totals ride the *collapsed* header; only `grok.expandCommandOutputs` / the latch open rows. The native `open diff →` link (→ `sidebar.ts` diff editor) stays for the full side-by-side. `summarizeTools` counts edits by unique `toolFilePath` so "Edited N files" matches the deduped header totals.
- **Generated media (v1.4.x).** `/imagine` (`image_gen`, or `image_edit` for reference-photo edits) and `/imagine-video` (`video_gen`; older/Linux builds `image_to_video`) are subscription-only and do **not** return ACP image blocks — grok writes the file into its session dir (`images/*.jpg`, `videos/*.mp4`) and reports the path as a JSON string in the completed tool result's `text` content. The pure `isMediaGenToolCall`/`extractGeneratedMediaPaths` (in `acp-dispatch.ts`) detect the tool and parse the path (image-vs-video by extension); `acp.ts` tracks the tool-call id (the *completed* update has a null title) and emits `mediaContent`; `sidebar.ts` `postGeneratedMedia` serves the file via `webview.asWebviewUri` (streamed from disk under the grok-home `localResourceRoot`; a base64 `data:` URI is the fallback for files outside the served roots). CSP grants `img-src`/`media-src ${webview.cspSource} data:`. Inline media is capped at 320px with Copy-path / Open-in-VS-Code hover actions. On resume grok replays it as a single collapsed `tool_call` carrying title + path together. Wire format + probes: `research/image-generation.md`.
- **Subagent rows.** A delegation is a tool call whose `_meta["x.ai/tool"].name` is `spawn_subagent` (grok-build) or `Task` (the Composer agent) — that marker is **authoritative both ways** for the pure classifier (`isSubagentToolCall`, `webview-helpers.js`): grok titles Grep/Read calls with their query/filename, so a grep FOR "spawn_subagent" is titled exactly that and title matching false-cards; without `_meta`, exact tool names + `rawInput.subagent_type` + the legacy background heuristics apply (the `get_command_or_subagent_output` poller stays excluded). The row renders *Subagent · \<description\>* (never downgraded by Composer's untitled completion update — `setSubagentTitle`) with blink-dots, then a duration stamp and a click-to-expand result under an "Output of the subagent:" label; `cleanSubagentOutput` strips the CLI envelope (plumbing tags, lead-ins, one wrapping `<response>` pair, the Agent ID hint) — every pattern optional and never throwing. Completion shapes differ: grok-build's foreground `tool_call_update` carries `rawOutput.SubagentCompleted` (output + duration_ms); Composer's carries only untitled text (`rawOutput {type:"Text"}`, no duration); a **background** spawn "completes" instantly with a started-ack (skipped — not the result) and its real output arrives on the `get_command_or_subagent_output` poller's `TaskOutput`, matched back to the card by task id (`maybeFinishSubagentFromTaskOutput`). **On cold `session/load` that poller output is FLATTENED to a text blob** (`=== Task … === / Command: [subagent:…] / … / === Output ===`, not the live structured shape), so the restore path parses it back with the pure `parseSubagentTaskResult` (`webview-helpers.js`, subagent-only — a backgrounded shell command polls the same tool and is left as a normal row) and `maybeFinishSubagentFromTaskText` folds it into the card + drops the redundant poller row (else a restored background delegation showed a stuck card + a raw `[subagent:…]` row). **Failure/cancel are threaded through BOTH the tool-channel completion AND the lifecycle rail** (a completion routinely races ahead of the lifecycle, so the marker can't live only on one) — a failed card reads red (`.subagent-failed`), a cancelled one muted (`.subagent-cancelled`); `finishSubagentCard`'s already-done early-return upgrades a late status marker, not just a late duration. The restore-created card is marked `subagentReplayed` and excluded from **live** lifecycle matching (mis-attribution guard) but NOT during replay (`state.replaying || !replayed`), so it still consumes its own re-forwarded lifecycle. The `subagent_spawned`/`subagent_finished` lifecycle stream is delivered **two ways**: on the LIVE `_x.ai/session_notification` rail (→ `xaiNotification`; the pure `isSubagentLifecycleUpdate` in `acp-dispatch.ts` re-routes it to the same `subagentUpdate` channel the webview consumes) and on the persist/replay `_x.ai/session/update` rail (→ `subagentLifecycle` → `subagentUpdate`, for `session/load`). `subagent_finished` fills `duration_ms` + the child's output — the duration Composer's tool-channel completion lacks (probe-confirmed on 0.2.101; earlier 0.2.93 measurements watched only the persist rail, which never fires live, hence the old "the CLI only logs these" note). FIFO spawn-tagging + child-id matching keep the right card. A history replay settles never-completed rows at replay end. Child tool calls are **not** streamed on the parent connection — deliberately no nested inspector. grok persists each child as a **top-level sibling session** with `session_kind: "subagent"` — the history list hides those (`SessionListEntry.kind` from `buildEntry`, filtered in `postSessionsList`, which pages by index slots consumed — the `nextOffset` field on the `sessions` message — so hidden rows can't stall or duplicate load-more). Real wire capture: `test/fixtures/composer-subagent-session.jsonl` (replayed end-to-end by `test/subagent-replay.dom.test.ts`); deep-dive: `research/subagents.md`.
- **Logout (#13).** `grok.logout` command + gear-menu *Sign out* → `sidebar.logout()` runs `grok logout`, disposes the session, shows the auth-required onboarding.

## Known limits

- Subagent rows show the task + result, not the child's own tool calls — those are never streamed on the parent ACP connection (a nested inspector would have to read the child session from disk; deliberate non-goal)
- Generated media is accepted only after realpath containment beneath the active session's `images/` or `videos/` directory; files under the Grok-home resource root stream through `asWebviewUri`, while a custom Grok home uses base64 after the same containment check
- No worktree UI
- The native diff editor is preview-only: it reconstructs full-file context from the file on disk and Grok's replaced-region metadata, but falls back to the region alone if the file is unreadable, oversized, or no longer matches; the write happens via `fs/write_text_file` after approval
- View placement: **default-homed in the Secondary Side Bar** (`viewsContainers.secondarySidebar` — requires VS Code ≥1.106, the `engines` floor; older hosts can't install this build — **Antigravity is on base 1.104** and refuses it, keeping the last compatible version). Relocation is one-click via gear → Config & debug → **Move view** (direct `vscode.moveViews` into the per-location containers — `src/view-move.ts`), or drag. Cursor's primary-side-bar context menu still hides the built-in "Move To" entry — the gear mover is the workaround. User moves persist; a persisted placement wins over the contribution default (*Reset Location* restores the default)

## Cross-platform notes

- `terminal-manager.ts` selects the shell via `resolveTerminalShell(platform, resolve, pref)`: Windows runs the agent's commands under PowerShell (`pwsh.exe`→`powershell.exe`, else cmd.exe via `shell:true`) to mirror the standalone CLI (#46); everywhere else `shell:true` → `/bin/sh`. Node runs a string shell as `<shell> -c "<command>"` (pwsh + Windows PowerShell both accept `-c`, and Node passes the command string through faithfully — embedded double quotes / JSON / paths-with-spaces survive; only cmd/bash-style `\"` escaping doesn't, which grok won't emit for a PowerShell target). `whichOnPath` skips the `\WindowsApps\` Store-alias stub. `grok.terminalShell` (`"auto"`|`"cmd"`, host-read → `setTerminalShellPreference`, cache-clearing) is the escape hatch back to cmd. Don't hardcode shell paths. **The agent is told which dialect to WRITE for** via `GROK_SHELL` in its spawn env (`buildEnv` in `sidebar.ts` sets it from the pure `grokShellEnvValue(resolvedTerminalShell(), platform)` — `pwsh`/`powershell`/`cmd` on Windows, unset on POSIX, and never overriding a user-set value): grok's ACP mode otherwise describes the shell from its own host detection and can emit POSIX idioms for a PowerShell host (§2.9; the `Shell:` line in the model's first message tracks `GROK_SHELL`, `research/oss-surfaces-probe.cjs`). **The `pwsh`-vs-`powershell.exe`-fallback gap is real: Windows PowerShell 5.1 collapses any non-zero native exit to 1 (pwsh 7 preserves it) and rejects `&&`/`||` chains (pwsh 7 accepts them) — install pwsh 7 for full parity.** A fresh shell spawns per command, so the profile re-runs each time (matches standalone's reachable functions, but adds latency and any profile stdout can prepend to captured output; on a `Restricted` execution policy 5.1 skips the profile + warns). The agent only acts on zero-vs-non-zero, which is preserved. Root cause + probe evidence: `research/powershell-terminal.md`.
- `cli-locator.ts` reads `HOME` / `USERPROFILE` env vars first (testability), falls back to `os.homedir()`. Uses `where` on Windows, `command -v` elsewhere. Checks `.cmd`/`.exe`/`.bat` extensions on Windows.
- Tests use `node -e "..."` everywhere, so commands are deterministic across platforms — don't add `pwd`, `awk`, `sleep`, `true`, etc.

## Publishing

**Release procedure — ALWAYS tag + create a GitHub Release (with the `.vsix` attached) on a release push to `main`** (standing convention; mirrors the `v1.0.0…` tag history + GitHub Releases):

**The whole procedure below (steps 2–5) is scripted** — after bumping the version + writing the changelog section (step 1, user-initiated), just run:

```bash
pwsh scripts\release.ps1        # Windows (native) — what we use here
./scripts/release.sh            # macOS / Linux / WSL
```

It reads the version from `package.json`, runs the gate, builds the vsix, commits the working tree (`-MessageFile`/`-Message` override the default `Release vX.Y.Z`), pushes `main`, creates the annotated tag, and runs `gh release create` **with the vsix attached** — extracting the matching `## X.Y.Z` changelog section as the release notes. `-DryRun`/`--dry-run` previews; `-NoTest`/`--no-test` skips the gate. It refuses to run off `main` or when the tag already exists (i.e. the version wasn't bumped). The script does **not** call `vsce`/`ovsx`, and there is **no publish workflow** (`.github/workflows/` is just `ci.yml`) — so the GitHub Release does **not** auto-publish to any store. Store publishing is split by who runs it (step 6): the agent **always publishes Open VSX right after the script succeeds** (part of every release, no separate ask); the **VS Code Marketplace** is manual and Paweł-only.

What the script encodes, step by step:

1. Bump `version` in `package.json` (user-initiated) and add the dated section to `CHANGELOG.md`. As part of this pass, **review the release-facing docs for staleness against what actually ships** — this review is a required step, not optional:
   - `README.md` — features / screenshots / install matrix.
   - **`README.marketplace.md` — the STORE listing, and a separate file.** `npm run package` ships it via `vsce package --readme-path`, so this is what the VS Code Marketplace and Open VSX render; `README.md` is only the GitHub page. Every edit to one is a decision about the other: the two carry the same feature list (keep the ordering in step), but deliberately different heroes — the listing sells the **extension**, so a desktop-app screenshot is off-message there. Its images are absolute `raw.githubusercontent.com/…/main/…` URLs, so **deleting or renaming anything under `docs/screenshots/` breaks the published store page** — remotely, after the release, with nothing local to notice. 3.2.1 shipped exactly that (alt text and a broken-image icon on Open VSX) because only `README.md` was updated. `test/readme-images.test.ts` now fails on a dangling reference in either file; it does not check that the two agree on content, which stays a judgement call.
   - `TESTS.md` — test plan vs. what actually ships.
   - `CLAUDE.md` — the project map (§ Module map, § ACP surfaces, § Known limits, the test-count floor): does it still describe the current architecture? It deliberately **doesn't** hardcode the version (it points to the changelog), so it needs no version edit — but its prose can go stale as behavior changes.
   - `docs/architecture.md` — the architecture doc: keep it in sync with new modules / event flows / surfaces.
   - `package.json` itself — description, `engines`, `categories`, `contributes`.

   Keep `CHANGELOG.md` entries **terse** (1–3 bullets per release under Added/Changed/Fixed; deep detail belongs in commits / `research/`, not the changelog); releases before the current minor live in `docs/CHANGELOG-ARCHIVE.md` (linked from the foot of `CHANGELOG.md`).
2. `npm test` (2659-test floor, all green) + `tsc -p . --noEmit` clean + **`npm run test:integration`** (the real Extension Host — `npm test` is only CI's `test` job, and CI runs this as a SECOND required job; without it a release can be tagged and published before CI goes red), **and `npm run test:live` against real grok — mandatory, run without asking**. The `release.*` scripts **now run BOTH `test:integration` and `test:live` by default** as part of the gate (`-SkipIntegration`/`--skip-integration` and `-SkipLive`/`--skip-live` are the explicit escape hatches); running it by hand first is still wise since the scripts also commit/tag/push once it's green.
3. **Repo-hygiene check, then** commit + push to `main` (direct-to-main, no feature branches). Never `git add -A` blind: run `git status --short` AND `git ls-files --others --exclude-standard`, and read the untracked list before staging. Anything machine-specific or agent-local that isn't ignored gets added to `.gitignore` in the same commit rather than committed and cleaned up afterwards — this repo is PUBLIC, so a stray file is published, not just committed. Offenders seen untracked-and-unignored: `.claude/settings.local.json` (machine-specific tool permissions) and ad-hoc `.verification/` output dirs left by an agent. Also confirm nothing under `media/` was hand-edited that a downstream consumer regenerates.
4. **Annotated git tag** `vX.Y.Z` at the release commit → `git tag -a vX.Y.Z -m "Release vX.Y.Z"` → `git push origin vX.Y.Z`.
5. **GitHub Release** for that tag → `gh release create vX.Y.Z --title "Release vX.Y.Z" --notes-file <notes> <vsix>` (notes = the new changelog section(s); include any earlier version that was bumped but never released). **Always attach the built `grok-vscode-phuryn-X.Y.Z.vsix` as a release asset** so the exact installable build is downloadable from the release.
6. **Store publish — split by store.**
   - **Open VSX: ALWAYS published by the agent as part of every release** (immediately after step 5, no separate ask) — `npx ovsx publish grok-vscode-phuryn-<version>.vsix -p <key>` with the key read from `OPEN_VSX_API_KEY` in the git-ignored `.env` at the repo root (never print or commit the key).
   - **VS Code Marketplace: manual, Paweł-only.** `npm run publish` (vsce; the `PawelHuryn` publisher is registered + authenticated locally). The agent never runs this — Paweł publishes it himself.
   - **Never announce a store as "live now."** A successful `ovsx publish` is NOT public availability — Open VSX scans new versions before listing them. In issue comments / user-facing messages, say **"~10 minutes"** for BOTH stores (Open VSX and the VS Code Marketplace alike).
   Publishing ≠ tagging either way.

Don't skip the tag/release (or the vsix asset) on a release push. (A pure mid-dev version bump that isn't a release — e.g. the unreleased v1.3.0 voice iteration — is the only exception.)

## Repo conventions

- **Work on `main`, synced to `origin/main`.** `main` is the only working line — start every task from `main` fast-forwarded to `origin/main`. The `dev` branch is **abandoned** (stale far behind `main`); do **not** develop on it. If the working tree is on `dev`, or `main` is behind `origin/main`, switch to `main` and `git reset --hard origin/main` before doing anything else (the published version lives on `main` — a stale checkout will look many versions behind and misnumber the changelog).
- Direct-to-`main`, no feature branches
- **Never commit or push automatically.** Changes reach `main`/`origin` only on the user's **explicit** request (rare) or as part of a release. Otherwise: build + reinstall locally for testing and leave the working tree uncommitted.
- Commits explain the *why*, not the *what*
- Don't introduce abstractions speculatively
- Don't add comments that explain what well-named code already says
- **Keep `CLAUDE.md` a current-state map** (see the editing-discipline note under § Status): rewrite changed behavior in place, never append changelog narrative or bug post-mortems here — link `research/*.md` / CHANGELOG instead
- 2659 tests is the floor — every PR should keep that green. All tests are grok-free (no binary spawn); grok-dependent probes live in `research/*.cjs` and are run manually, never by `npm test` or CI. **On macOS, 6 of them fail locally** (`test/project-discovery.test.ts`, `test/desktop-host-pure.test.ts`): they compare `os.tmpdir()` against its realpath, and `/var` is a symlink to `/private/var` there but `/tmp` is real on the Linux CI box. Reproduces on a pristine upstream checkout — not a fork regression, so don't "fix" it by weakening the assertions
- **Rebuilding clears older `.vsix` first** — `npm run package` (and the install/release scripts) delete stale `grok-vscode-phuryn-*.vsix` before building, so only the current version is on disk. After any doc or code change, rebuild + reinstall so the installed extension's bundled docs are current. **Package last:** the vsix bundles `CLAUDE.md`/`README.md`/`docs/` as files, so finish *all* doc + code edits **before** the final `npm run package` + reinstall — otherwise the installed build ships a stale-docs snapshot. If you rebuild mid-task and then touch docs again, rebuild again so the order is always edit-everything → package → reinstall.
- **Version bumps are user-initiated.** Iterate at the current version (rebuild the same vsix and reinstall locally) until the user says to bump and publish. Don't bump `package.json` on your own. When Paweł asks for a release, the default is a **patch** bump (+0.0.1); **any minor or major bump requires his direct, explicit approval** — never infer it from the size of the change.
- **Releasing requires a direct instruction to release — a version number alone is never one.** Only an unambiguous imperative ("release it", "publish 2.0.3", "run the release script") authorizes the § Publishing procedure. Naming a version in any other role does **not**: *"tell them it ships in 2.0.3"*, *"put this under 2.0.3 in the changelog"*, *"this would be a 2.0.3"* are all scope/labelling statements, and treating one as an authorization ships an unrequested tag, GitHub Release, and Open VSX publish — three externally-visible, effectively irreversible actions. The same applies to a release named inside a larger request: the imperative must attach to *releasing*, not to the work. Default to doing the work, leaving the tree uncommitted, and reporting it as ready to release. **In any doubt, ask** — a one-line question costs nothing next to an unrequested publish.
- **Sign GitHub comments.** Every GitHub issue/PR comment posted on the user's behalf ends with a signature on its own final line (italic). Pick by whether Paweł actually reviewed the text before it was posted: if he reviewed it, use `_Written with an agent, reviewed by Paweł_`; if the agent posted it without his review, use `_Written by Pawel's agent_`. Only claim review when it actually happened.
- **The `phuryn` GitHub account is Paweł** — the user you are working with and the repo owner. Unsigned comments from `phuryn` are his own words (don't read them as a third party's); agent-posted comments carry the signatures above.
